# المنهجية العامة لإدارة وتطوير ونشر المشاريع على VPS
**الإصدار:** 1.0  
**تاريخ الاعتماد:** 2026-11-05  
**الحالة:** سياسة عامة معتمدة؛ التنفيذ التقني لكل مشروع يتطلب فحصًا منفصلًا وموافقة على الإنتاج.  
**النطاق:** مشاريع الويب والخدمات الخلفية وقواعد البيانات وتطبيقات Flutter، على الأجهزة المحلية وVPS.

> **القرار المعماري:** Git/GitHub للمصدر والمراجعة والتوثيق، CI للاختبارات والبناء، سجل Docker خاص (Private OCI Registry) للصور، وDocker Compose للنشر على VPS. تدار الإصدارات بمُعرّف صورة غير قابل للتغيير (digest)، مع موافقة صريحة قبل الإنتاج. لا يُشترط أن يكون GitHub هو وسيلة النقل إلى VPS.

## 1. الأهداف والمبادئ
- المحافظة على سلامة المصدر والبيانات والإنتاج والقدرة على استرجاع التشغيل.
- فصل **المصدر** عن **المنتج القابل للنشر**؛ لا يلزم وجود نسخة Git للمشروع داخل VPS الإنتاجي.
- فصل التطوير، الاختبار المعزول، ما قبل الإنتاج، والإنتاج حسب حجم المشروع.
- تفضيل Docker Compose على Kubernetes للمشاريع الحالية، وتجنب إدخال لوحة نشر جديدة دون دراسة.
- اعتماد مبدأ **افحص قبل أي تعديل** مع أقل نطاق تغيير ممكن؛ لا حذف أو reset أو clean أو force-push.
- عدم الدمج إلى الفرع المحمي أو النشر إلى الإنتاج دون موافقة المستخدم الصريحة.
- كل مرحلة تنتهي بتقرير: المنجز، الاختبارات، المتبقي، المخاطر، جاهزية الإنتاج، وخطوة تالية واحدة واضحة.

## 2. البنية القياسية
```text
Developer (Ubuntu/Windows)
    |
    v
Private GitHub repository -> Branch / PR / review
    |
    v
CI + isolated tests + security checks + build
    |
    v
Private OCI registry (image: version AND immutable sha256 digest)
    |
    v
Manual production approval
    |
    v
VPS: Docker Rootless + Compose + reverse proxy + health checks
    |
    +--> PostgreSQL persistent volumes / backups
    +--> monitoring, logs, alerts, documented rollback
```

**الاختيارات الافتراضية:**
1. مصدر الكود: GitHub خاص ما لم يقرر المشروع بديلًا خاصًا مثل Forgejo/Gitea.
2. الحزم: صور OCI خاصة لخدمات Go وNext.js وغيرها، مُوقّعة/مُتحقق من مصدرها حيثما أمكن.
3. CI/CD: GitHub Actions حاليًا أو أداة CI أخرى مستقبلًا، مع خطوات فحص ثم بناء ثم رفع إلى السجل، ولا نشر إنتاج تلقائي.
4. سجل الصور: سجل خاص مثل GHCR private أو Registry ذاتي، بعد تقييم الصلاحيات والتكلفة والتوافق؛ لا يُفرض مزود قبل تجربة عملية.
5. التشغيل: Docker Compose على VPS عبر Docker Rootless حيث هو قائم، دون تغيير socket أو network أو proxy بلا تدقيق.
6. البيانات: PostgreSQL مستقل عن دورة حياة صورة التطبيق؛ volumes مستقلة، ومبدأ نسخ احتياطي مجرَّب.
7. الأسرار: تبقى في مدير أسرار أو إعدادات خادم مقيدة الصلاحيات، ولا تُكتب في Git أو صور Docker أو السجلات.
8. لوحة مركزية مثل Coolify أو Dokploy: **اختيارية فقط**، تُختبر في بيئة منفصلة أولًا؛ ليست شرطًا للمنهجية.

## 3. دورة حياة التغيير
### المرحلة A: الاستكشاف للقراءة فقط
- إثبات هوية المشروع، المستودع والفرع وHEAD والحالة المحلية والـ remote.
- مراجعة قائمة التغييرات والملفات غير المتتبعة والـ staging دون إزالتها.
- جرد الخدمات والمنافذ وصور Docker وVolumes والهجرة الحالية والتبعات والموارد.
- تسجيل baseline وSHA للمرشح والنسخ الاحتياطية ونطاق العمل.
- يمنع استخدام `git reset --hard`، `git clean`، الحذف الجماعي، وإعادة بناء إنتاجية غير معتمدة.

### المرحلة B: التطوير المعزول
- إنشاء branch/working tree أو نسخة معزولة محددة المصدر.
- إعداد قائمة ملفات متوقعة (manifest) والالتزام بأصغر نطاق تغيير.
- حماية عمل المطورين الآخرين والملفات غير المتتبعة.
- كل إصلاح يجب أن يتضمن اختبارات ملائمة ووثائق إذا تغير السلوك.

### المرحلة C: التحقق
- تنسيق / lint / تحليل ثابت / unit / integration / HTTP E2E بحسب التقنيات.
- اختبار قواعد البيانات على قاعدة معزولة؛ التحقق من الترحيلات صعودًا والتوافق أثناء التحديث.
- مراجعة التحكم في الصلاحيات وعزل المستأجرين والطلبات غير المصرح بها، وتجنب نشر الأسرار.
- تقرير نتائج PASS/FAIL والأدلة، وعدم اعتبار «وجود الاختبار» دليلًا على نجاح تشغيله.
- فصل اختبارات خادم Linux عن اختبارات Flutter على الأجهزة/المحاكيات المطلوبة.

### المرحلة D: بناء الإصدار
- البناء في CI أو جهاز بناء موثوق ومعزول، لا داخل خدمات VPS الحية.
- تثبيت نسخ التبعيات قدر الإمكان، فحص الثغرات والتراخيص والملفات السرية، واستخدام Docker multi-stage.
- رفع الصورة إلى Registry خاص؛ تسجيل SHA الخاص بالـ commit وSHA256 digest للصورة ونسخ التبعيات.
- التمييز بين `tag` للقراءة و`digest` للنشر الفعلي؛ لا تستخدم `latest` للإنتاج.
- إن تعذرت الشبكة، يسمح بنقل صورة مُتحقق من checksum عبر SSH كمسار استثنائي، مع حفظ الأدلة.

### المرحلة E: ما قبل الإنتاج
- سحب الصورة نفسها باستخدام digest على بيئة staging.
- فحص الاتصالات والـ proxy وTLS وhealth/readiness وقيود المستخدم والصلاحيات ومهام الخلفية.
- التحقق من توافق إصدار التطبيق مع مخطط قاعدة البيانات، وإجراء اختبار استعادة نسخة احتياطية دوريًا.
- إعداد خطة نشر موثقة وخطة تراجع وحدود قبول واضحة.

### المرحلة F: موافقة ونشر
- لا يُنفذ أي تغيير في الإنتاج قبل موافقة صريحة على **إصدار محدد ونطاق تغييرات محدد**.
- نقطة فحص قبل النشر: backup verified + disk/memory capacity + image digest + migration plan + rollback.
- إن كانت الترحيلات حساسة، تُستخدم طريقة expand/migrate/contract بمراحل توافقية بدل تغييرات تدميرية.
- سحب الصورة المعتمدة، تحديث متغير الصورة فقط في Compose، ثم تطبيق تحديث متحكم به؛ الانتباه إلى أن Compose لا يقدم نشرًا بلا انقطاع تلقائيًا.
- تحقق بعد النشر: صحة الخدمات وAPI، الاتصال بالقاعدة، عمليات أساسية، السجلات والأخطاء وزمن الاستجابة.
- التراجع يعيد **التطبيق** إلى digest السابق، لكن **قاعدة البيانات لا تُرجع تلقائيًا**؛ قد يتطلب تراجعها خطة استعادة مستقلة مع آثار فقد بيانات يجب تقييمها.

### المرحلة G: التوثيق
يُكتب تقرير كل مرحلة يحتوي:
```text
PROJECT=
PHASE=
DATE=
BASELINE_SHA=
CANDIDATE_SHA=
EXPECTED_CHANGED_FILES=
ACTUAL_CHANGED_FILES=
TESTS_RUN=
TESTS_PASS_FAIL=
IMAGE_DIGEST=
DATABASE_MIGRATIONS=
BACKUP_STATUS=
PRODUCTION_CHANGES=NONE|APPROVED_AND_RECORDED
COMPLETED=
REMAINING=
RISKS=
PRODUCTION_READY=YES|NO|CONDITIONAL
NEXT_STEP=
```
ويضاف سجل إصدار (Release Notes) عند كل إصدار مرشح أو إنتاجي.

## 4. حدود الأمان والصلاحيات
- منح CI صلاحية قراءة المصدر والكتابة إلى Registry فقط عند الحاجة؛ لا توضع مفاتيح root أو SSH طويلة العمر في CI بلا ضرورة.
- تفضيل صلاحيات ضيقة ومفاتيح قصيرة العمر / OIDC عند دعم المزوّد، مع حماية البيئات والموافقات.
- حماية فروع main وإلزام المراجعة والاختبارات حسب إعدادات المستودع.
- منع secrets و.env الحقيقي وملفات backup وبيانات المستخدم من الدخول إلى Git أو artifacts العامة.
- التحقق من حدود وصول Registry، وإدارة تدوير الرموز وسحب الصلاحيات.
- عزل شبكات التطبيقات وقواعد البيانات مع وصول داخلي فقط إلى قاعدة البيانات، وحماية النسخ الاحتياطية واختبار الاسترداد.
- Docker Rootless لا يلغي ضرورة العزل وإدارة الأسرار والتحديثات وحماية VPS.

## 5. سياسة قواعد البيانات
- لا تعديل على PostgreSQL الإنتاجي قبل جرد schema والإصدارات والنسخ الاحتياطية.
- لكل ترحيل: رقم/اسم، checksum، اختبار معزول، أثر الأداء/الأقفال، توافق الإصدارات، وخطة تعامل مع الفشل.
- النسخ الاحتياطية آلية، مشفرة حيث يلزم، تُحفظ خارج الخادم مع سياسة احتفاظ وفحص استعادة.
- لا تنفيذ أوامر DROP/TRUNCATE أو إعادة تهيئة قواعد أصلية دون طلب صريح وتحليل أثر.

## 6. تطبيقات Flutter
- Git وPR وCI واختبارات analyze/unit/widget/integration هي القاعدة.
- حزم التسليم APK/AAB بدلاً من OCI images، مع رقم إصدار وبناء وhash وتوقيع مؤمن.
- إدارة مفاتيح التوقيع والتوزيع في قنوات خاصة؛ لا رفع مفاتيح إلى المستودع.
- إجراء اختبار على جهاز فعلي/محاكي قبل اعتماد الإصدار.
- لا تدخل تغييرات Flutter في نطاق مشروع ويب يطوره فريق مختلف إلا بطلب واضح.

## 7. تطبيق المنهجية تدريجيًا على المشاريع القائمة
1. **المرحلة صفر (الآن):** توثيق المنهجية فقط؛ لا تغير البنية التحتية ولا الخدمات.
2. **المرحلة الأولى:** اختيار خدمة غير حرجة وفحص Dockerfile وCompose والـ registry والـ reverse proxy الحالي للقراءة فقط.
3. **المرحلة الثانية:** إنشاء pipeline لبناء صورة تجريبية ونشرها على staging مع ربط digest وتوثيق النتائج.
4. **المرحلة الثالثة:** اعتماد سجل صور خاص ومنهجية rollback والنسخ الاحتياطية، ثم تجربة نشر بإذن صريح.
5. **المرحلة الرابعة:** تعميم النمط على بقية الخدمات بعد إثبات نجاحه.
6. **المرحلة الاختيارية:** تقييم Coolify/Dokploy على خادم معزول؛ عدم تثبيتهما في الإنتاج الحالي كخطوة أولى.

**ملاحظات حسب المشروع:**
- منصة مصانع المياه: أكثر حساسية بسبب الماليات والورديات والمبيعات المؤجلة، فتُشدد اختبارات E2E وعزل المصانع وترحيلات قاعدة البيانات.
- نظام معهد ابن عباس ومركز الحافظات: تُحمى البيانات التعليمية وحسابات المستخدمين والمرفقات وتُختبر صلاحيات النشر.
- مشاريع Docker القائمة: لا تُستبدل Docker Rootless أو شبكة Reverse Proxy أو المنافذ الحالية دون تدقيق وتخطيط مسبق.

## 8. معايير جاهزية الإنتاج (Release Gate)
لا يعتبر الإصدار جاهزًا حتى تتوفر الأدلة التالية:
- المصدر والنطاق والتغييرات متحقق منها؛ ولا فقدان لأعمال سابقة.
- الاختبارات المطلوبة ناجحة أو توجد استثناءات موثقة ومقبولة.
- الصورة مبنية ومثبتة digest ومصدرها موثق.
- لا أسرار مكشوفة ولا ثغرات حرجة غير معالجة دون قبول مخاطر صريح.
- نسخة احتياطية سليمة وخطة استعادة مجربة بحسب حساسية النظام.
- خطة ترحيل قاعدة بيانات متوافقة وخطة تراجع قابلة للتطبيق.
- فحوص صحة ومراقبة وسجلات ومسؤول نشر محدد.
- موافقة صريحة على النشر الإنتاجي مع نافذة وتواصل مناسبين.

## 9. ما لا تفعله هذه الوثيقة
- لا تنفذ نشرًا، ولا تُعدّل VPS، ولا تنشئ أسرارًا أو تغيّر Registry قائمًا.
- لا تفترض أن CI أو الترحيلات أو الاستعادة جاهزة قبل التحقق الفعلي.
- لا تمنح صلاحية دمج PR أو النشر تلقائيًا.
- لا تمنع استخدام Gitea أو Forgejo أو SSH؛ هذه بدائل يمكن اعتمادها عند وجود مبرر.

## 10. المراجعة والتغيير
أي تغيير جوهري في المنهجية يمر عبر PR مستقل موثق يشرح السبب والتأثير وخطة الانتقال، ويُعتمد قبل تطبيقه على الأنظمة الإنتاجية.

---
**الخلاصة:** احتفظ بـ GitHub لإدارة الشيفرة والتوثيق، لكن اجعل النشر مبنيًا على OCI images مختبرة ومحددة digest، باستخدام Docker Compose ضمن VPS الحالي، مع أمان البيانات والمراجعة والموافقة البشرية قبل الإنتاج.
