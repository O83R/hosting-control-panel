# برومبت تأسيس VPS جديد مماثل لبنية تشغيل خادمي الحالي — بدون بيانات

أنت مهندس بنية تحتية SRE/DevOps وخبير Ubuntu وRootless Docker. المطلوب تنفيذ **تأسيس خادم VPS جديد مستقل** يستضيف مواقع مختلفة، باستخدام ملفات هذا المجلد، وليس نقل موقع أو محتوى الخادم الإنتاجي الحالي.

## سياق مثبت
اقرأ `CURRENT-VPS-BASELINE.md`؛ البنية القديمة تضم Ubuntu/Linux مع 4 vCPU و8 GiB RAM تقريباً (نسخة Ubuntu على المصدر غير مؤكدة)، ext4، cgroup v2 + systemd، Docker رئيسياً لخدمات مشتركة، ومحركات Rootless مستقلة للمشاريع، وNginx Proxy Manager وUptime Kuma على شبكات مراقبة/Proxy منفصلة. كان Rootless مستخدم بلا حاويات يستهلك ~1 GiB، فتم إيقافه مؤقتاً بنجاح. توجد عمليات Chromium zombie في مشروع قديم ويجب عدم تكرار تصميم لا يدير أبناء المتصفح. النسخ القديمة تعمل كمهام systemd، لكن يجب اختبار قابلية استعادة النسخ الجديدة قبل الإنتاج.

## النطاق
- تأسيس **Ubuntu Server 24.04 LTS نظيف** على VPS جديد فقط؛ إن كانت صورة المزود أو أحدث توافق Docker مختلفة فتوقف وراجع توافقها قبل العمل.
- تدقيق الوصول بوساطة SSH key، الوقت والمنطقة الزمنية، DNS والنطاقات، التخزين، الإصلاحات الأمنية، سياسة إعادة التشغيل، النسخ الاحتياطية، المراقبة، الجدار الناري بالتنسيق مع جدار المزود.
- تثبيت أدوات أساسية، Docker Engine من المستودع الرسمي، Compose plugin، rootless extras، مستخدمي تطبيقات **جدد** حسب العدد المطلوب فقط.
- شبكة Proxy ومراقبة مع NPM وKuma؛ منافذ الإدارة loopback فقط؛ إعدادها لاحقاً عبر نفق SSH أو TLS محمي.
- اجعل كل عملية قابلة للإعادة وخاضعة لاختبار صلاحية أو `plan`، مع أدلة PASS/FAIL، وتراجع وتوثيق.
- جميع قواعد البيانات والمحتويات والنطاقات والشهادات والتوكنات الخارجية تحتاج توفيراً جديداً، وليس استنساخ الأصل.

## قواعد إلزامية
1. **لا تلمس الخادم القديم** مهما كانت الأسباب؛ كل أوامر التنفيذ يجب أن تتأكد من `--expected-hostname` وأن المضيف جديد.
2. ابدأ بقراءة فقط ثم بخطة تنفيذ محددة؛ لا تشغل `--apply` دون تفويض واضح ومراجعة المخرجات.
3. لا تطلب نشر بيانات سرية في المحادثة أو GitHub. استخدم مخزن أسرار/ملفات محلية chmod 600، ولا تطبعها في السجلات.
4. لا تغلق SSH، ولا تغير المنفذ أو تعطّل كلمة المرور أو تفعّل الجدار الناري تلقائياً قبل التأكد من مسار بديل للوصول.
5. لا تنفذ `prune` أو `down -v` أو `swapoff` أو إعادة تشغيل المضيف أو Docker الإنتاجي دون موافقة وصيانة.
6. لا تعتبر `docker ps` أو `Result=success` وحده دليلاً على صحة التطبيق أو قابلية استعادة البيانات.
7. لا تضع حدود CPU/RAM/PIDs موحدة عشوائياً؛ خطط ميزانية ذاكرة تشمل docker daemons + rootlesskit + قواعد البيانات + cache + هامش.
8. راقب RAM المتاحة وPSI وSwap si/so وCPU وDisk/inodes وOOM ونتائج النسخ واختبارات HTTP والسجلات، مع تنبيه خارجي مستقل عن VPS.
9. النسخ الاحتياطية تكون مشفرة، مع موقع خارجي، صلاحية احتفاظ، اختبار استعادة، وتنبيه عند التخلف، ولا تعتمد على مجلد محلي فقط.
10. ممنوع تغيير شيفرة أي مشروع أو مخططات قواعد بياناته في هذه المهمة. لا GitHub merge/deploy للإنتاج بلا إذن.

## سير العمل المطلوب
### A — جمع معطيات VPS الجديد
تحقق من `hostnamectl`، `lsb_release -a`، `free -h`، `df -hT`، `findmnt`، `ss -ltn`، `timedatectl`، `systemd`، `cgroup2fs`، `docker --version` إن وجد. لا تطبع أسراراً أو أي ملفات اعتماد. وضّح ما تم التحقق منه مقابل الافتراضات.

### B — التخطيط
اقترح المستخدمين الجدد (حد أدنى)، الشبكات والواجهات العامة/الداخلية، مخطط منافذ 22/80/443 وloopback للإدارة، الميزانية، الاختبارات، التراجع. اطلب موافقة على أي أثر على الوصول أو تكلفة أو بيانات.

### C — تأسيس الأساس
ابدأ `bash scripts/bootstrap-vps.sh --plan`، ثم استخدم مراحل `base` و`docker` و`users` فقط على الخادم الجديد وبمعرّف مضيف مطابق. لا تشغل المرحلة `users` إلا بأسماء حسابات جديدة مصرح بها. تأكد أن كل rootless Docker يعمل عبر systemd user service مع linger وcgroup v2؛ لا تعرض Docker API عبر TCP ولا تضف المستخدمين إلى مجموعة docker root إلا بإقرار مخاطرة واضح.

### D — خدمات مشتركة
راجع `monitoring/.env.example` وحدد صوراً مدعومة بإصدارات أو sha256 معتمدة؛ لا تعتمد على latest بلا مراجعة. نفّذ `scripts/deploy-monitoring.sh --plan` قبل التطبيق. أنشئ Proxy ومراقبة دون بيانات مستخدم. إعداد NPM وKuma يدوي/آمن بالاعتمادات الجديدة. اختبر الوصول عبر localhost والنفق وعدم ظهور 81/3001 للعامة.

### E — الأمان والتشغيل
التحديثات الأمنية دون reboot تلقائي، التسجيل الزمني، إدارة الأقراص، صلاحيات `/srv`، SSH key وملفات sudo المقيدة، قواعد Firewall مخططة مع اختبار جلسة SSH ثانية. اشرح أن `unattended-upgrades` قد يعيد تشغيل خدمات فردية أيضاً. لا تنشر HTTP إلى الخارج إلا بعد موافقة DNS/SSL.

### F — الحماية والاستعادة
حدد سياسة النسخ الاحتياطية لكل مشروع جديد بعد نشره، مخزن خارجي، مفاتيح منفصلة، test restore على isolated scratch، وأولويات الاستعادة. اجعل المراقبة خارج الخادم تغطي الـ VPS نفسه. اختبر إعادة تشغيل rootless user service في نافذة صيانة، ولا تعطل الإنتاج لإثبات ذلك.

### G — إغلاق المشروع
نفّذ `scripts/verify-vps.sh` وصنّف كل بند PASS/INCOMPLETE/FAIL، وأنتج تقريراً يحتوي إصدار النظام وDocker وCompose، الخدمات، الاستماع على المنافذ، النسخ الاحتياطية، المراقبة، مخاطر متبقية، والخطوات اللاحقة.

## مخرجات نهائية
- قائمة تهيئة مكتملة للخادم الجديد (دون أي بيانات موقع).
- أوامر تشغيل منفصلة وقابلة للتراجع، مع موافقات لكل مرحلة.
- ملف إعدادات عامّ خالٍ من الأسرار، ومخطط لتخزين الأسرار.
- جدول قدرات وعتبات تنبيه، ومخطط نسخ واستعادة مثبت بالأدلة.
- وثيقة تسليم لاستنساخ الإعدادات على خادم ثالث لاحقاً.

**لا تبدأ أي تنفيذ على المصدر أو على أي خادم مجهول الهوية؛ ابدأ بفحص الخادم الجديد وإثبات أنه نظيف وأنه لا يخدم إنتاجاً.**
